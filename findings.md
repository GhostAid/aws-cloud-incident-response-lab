# Incident Findings Report

## Executive Summary

This project simulated a compromised AWS IAM user account (victim-user) and analyzed the resulting CloudTrail logs. The objective was to identify suspicious activity, reconstruct a timeline, and evaluate the effectiveness of AWS security controls.

## Investigation Scope

The investigation focused on activity performed by the IAM user victim-user using AWS CLI commands that generated CloudTrail events.

 ## Observed Events

* GetCallerIdentity
* ListBuckets
* ListUsers
* CreateUser

All observed events originated from the source IP address 102.89.34.71.

 ## Key Findings

1. Credential Validation Activity

The GetCallerIdentity API call indicates that the user attempted to verify the validity of AWS credentials.

2. Resource Enumeration

The ListBuckets events suggest reconnaissance activity intended to identify available S3 resources within the AWS account.

3. IAM Enumeration

The ListUsers event indicates an attempt to discover IAM users and identify potentially privileged accounts.

4. IAM Account Manipulation

The CreateUser event indicates an attempt to create a new IAM user. If successful and followed by permission assignment or credential creation, this could support persistence or privilege escalation. In this simulation, the request was denied, so no new IAM user was created.

5. Effective Security Controls

All observed actions resulted in AccessDenied responses. This demonstrates that IAM permissions successfully prevented unauthorized access and privilege escalation attempts.

 ## Impact Assessment

No resources were modified or created during the simulation. The impact was limited because IAM policies restricted access to sensitive actions.

 Containment Actions

* Reviewed CloudTrail logs.
* Investigated suspicious API calls.
* Verified IAM permissions assigned to the user.
* Confirmed that unauthorized actions were blocked.
* Recommended ongoing monitoring and credential rotation.

 ## Detection Process

The investigation began by reviewing AWS CloudTrail events generated by the simulated compromised IAM user, `victim-user`.

The following sequence of API calls was identified:

1. `GetCallerIdentity` — credential validation
2. `ListBuckets` — S3 resource enumeration
3. `ListUsers` — IAM user enumeration
4. `CreateUser` — attempted IAM account manipulation

The events were correlated using the IAM username and source IP address `102.89.34.71`.

Each API request returned an `AccessDenied` response, indicating that the IAM permissions assigned to `victim-user` prevented the simulated actions from succeeding.

This investigation demonstrates how CloudTrail can provide the evidence required to identify suspicious API activity, establish an activity timeline, and determine whether attempted actions were successful or blocked.

## MITRE ATT&CK Mapping

The observed activity was mapped to relevant MITRE ATT&CK techniques based on the CloudTrail API calls recorded during the simulation.

| CloudTrail Event | ATT&CK Technique | Technique ID | Interpretation |
|---|---|---|---|
| GetCallerIdentity | Cloud Service Dashboard Discovery | T1538 | Attempt to obtain information about the current cloud identity/account context. |
| ListBuckets | Cloud Storage Object Discovery | T1619 | Attempt to enumerate available cloud storage resources. |
| ListUsers | Account Discovery | T1087 | Attempt to enumerate IAM identities within the AWS environment. |
| CreateUser | Account Manipulation | T1098 | Attempt to create an IAM identity. The request was denied, so no account was created. |

## ATT&CK Assessment

The observed sequence is consistent with cloud-environment discovery followed by an attempted IAM account manipulation action.

The mapping does not indicate that the techniques were successfully executed. All observed API requests returned `AccessDenied`, and the investigation found no evidence of successful resource creation, modification, or privilege escalation.

This demonstrates the importance of correlating CloudTrail activity with IAM authorization results when investigating suspicious cloud activity.

## Conclusion 
The investigation demonstrated how AWS CloudTrail can be used to detect and reconstruct suspicious IAM activity. The simulated user generates multiple discovery and IAM-related API requests, all of which were denied by AWS IAM policies. No evidence of successful resource modification, account creation, or privilege escalation was identified. The exercise highlights the importance of centralized logging , least-privilege IAM policies, and continuous monitoring in detecting and limiting unauthorized activity.
